# Remote Keyboard 協定 v4

- 版本：4（`protocolVersion` 的值）。與 v3 不相容，v3 的配對全部作廢。
- 適用對象：手機端（iOS 鍵盤延伸功能、主 App 的配對畫面，將來的 Android 鍵盤）與主機端（Mac、Windows、Linux 接收端）的所有實作。
- 效力：實作與本文件不一致時，修正實作；本文件有錯時，先改本文件。
- 設計依據：`docs/superpowers/specs/2026-11-10-windows-linux-receiver-design.md` §5、`docs/superpowers/specs/2026-11-01-trackpad-design.md` §6。

| 主機 | GATT central，也就是接收端 |
| `a ‖ b` | 位元組串接 |

## 1. GATT 結構與廣播

### 1.1 GATT 資料庫

鍵盤與配對畫面各自發布同一個 primary service，內容相同：

| 項目 | UUID | 屬性 | 用途 |
|---|---|---|---|
| service | `706AA642-68A3-41FA-889D-24E30709B0D0` | primary | |
| `event` | `C7FC0313-53E7-4DCD-B75F-2AE66FE9C586` | notify；不可讀、不可寫 | 手機到主機 |
| `control` | `320468E2-53B6-4B6A-88EC-AE2752415818` | write（有回應）；不可讀 | 主機到手機 |

- 兩個 characteristic 都不要求 BLE 層的配對或加密。身分驗證與加密全部在本協定內完成。
- `event` 的每一則 notification 是下列三種之一，由第一個位元組區分：

| 第一個位元組 | 內容 | 章節 |
|---|---|---|
| `0x02` | 一則 JSON 訊息的一個分段 | §2 |
| `0x03` | 一個指標封包 | §8 |
| 其他 | 主機略過，只記錄第一個位元組與長度。`0x7E` 保留給偵錯建置的量測通道，正式建置不送也不處理 | |

- `control` 的每一次寫入是一則完整的 `ControlMessage` JSON（§3.2），不分段。長度超過單次寫入上限時使用 ATT 的 prepare／execute 長寫入，手機依 offset 由小到大接回。一則 `control` 訊息不得超過 512 bytes。
- 手機對每一次 `control` 寫入都回 ATT 回應：內容能解成 `ControlMessage` 時回成功，否則回 Invalid Attribute Value Length（`0x0D`）。回應只表示格式可解，不表示訊息被採用。
- notification 的長度上限是該 central 協商後的可通知長度（ATT MTU 減 3）。已觀察到的最小值是 182 bytes。

### 1.2 廣播

廣播封包只放一個 128-bit service UUID，不放裝置名稱與其他資料。GATT 資料庫的 service UUID 不出現在廣播中。

| 廣播者 | 廣播的 service UUID | 掃描它的主機 |
|---|---|---|
| 鍵盤，已選定目前主機 | 該主機的選定 UUID（§1.3） | 只有該主機 |
| 鍵盤，沒有任何配對 | 不廣播 | |
| 配對畫面 | 配對 UUID `6BA36ECB-1BF9-49C1-B98D-37402247F356` | 只有配對時段開著的主機 |

使用者在鍵盤上切換目前主機時，鍵盤改廣播新主機的選定 UUID，並重設連線（中斷現有連線、丟棄握手與 session 狀態、重新發布 service）。

### 1.3 選定 UUID

```
d      = SHA-256("rk-select"(9) ‖ hostId(16))
b      = d 的前 16 個位元組，b[0] 到 b[15]
b[6]   = (b[6] AND 0x0F) OR 0x40
b[8]   = (b[8] AND 0x3F) OR 0x80
UUID   = b[0..3] - b[4..5] - b[6..7] - b[8..9] - b[10..15]，每個位元組寫成兩位十六進位
```

`b[0]` 對應 UUID 字串最左邊的兩個十六進位數字。

範例：`hostId` 為 `000102030405060708090a0b0c0d0e0f` 時，`d` 的前 16 個位元組是 `521f2ae3477fcee09a4014e35e4d35ee`，選定 UUID 是 `521F2AE3-477F-4EE0-9A40-14E35E4D35EE`。

### 1.4 主機的掃描

- 主機掃描自己的選定 UUID。配對時段開著時另外掃描配對 UUID，時段結束立刻停止掃描配對 UUID。
- 判斷依據必須是「這一筆廣播封包」所帶的 service UUID。不得使用作業系統或函式庫為同一個裝置累加的 UUID 清單，否則手機選過的每一台主機都會一直認為自己被選中。
- 連線期間停止掃描，斷線後恢復。
- 掃描層仍可能短暫看到過期內容，由握手的 `notSelected`（§6.3）接手。

各平台的做法與實測（2026-11-11，每個平台 21 次切換）：

| 平台 | 掃描方式 | 看到新 UUID 的延遲（中位數／最大） | 掃描時機 |
|---|---|---|---|
| Mac | CoreBluetooth，允許重複回報。每筆回報只帶當下的 UUID | 0.05／0.24 秒 | 接收工作階段啟動後才掃描 |
| Windows | WinRT `BluetoothLEAdvertisementWatcher`，主動掃描，逐筆廣播回報 | 0.23／1.0 秒 | 接收端執行期間持續掃描 |
| Linux | BlueZ D-Bus 探索；未連線時每 1.5 秒（Provisional）`StopDiscovery` 再 `StartDiscovery`，重啟時對目標裝置 `RemoveDevice` | 1.24／1.56 秒 | 接收端執行期間持續掃描 |

平台注意事項：

- Windows 與 Linux 不可使用 btleplug：它把同一個裝置看過的 service UUID 累加，UUID 消失時沒有任何事件。
- Linux 的控制器會過濾重複廣播，同一個裝置回報一次後，要到核心約每 10.8 秒重啟掃描時才再回報，所以必須定時重啟探索。BlueZ 的裝置物件會累加 UUID，所以重啟時要移除該裝置。切換後 1.5 秒內可能同時看到新舊兩個 UUID。
- Linux 的 `AdvertisementMonitor` 介面需要 `bluetoothd` 以實驗模式啟動，原始 HCI socket 需要 root，兩者都不使用。
- Linux 接收端可指定藍牙控制器，預設用 BlueZ 的預設控制器。連線期間停止定時重啟探索。
- Windows 的實測環境是預覽版 build 26300，正式版未驗證。

### 1.5 連線建立

主機看到目標廣播後依序：停止掃描、連線、找出 service 與兩個 characteristic、訂閱 `event`。訂閱成功後連線才算就緒，握手（§6）或配對（§5）由此開始。

| 項目 | 值 |
|---|---|
| 從開始連線到就緒的逾時 | 5 秒，逾時則取消連線並重新掃描 |
| 連線就緒前就失敗時，重新掃描前的等待 | 連續第 1 次立即，之後 0.5、1、2 秒，上限 2 秒（Provisional）。連線就緒一次即歸零 |

手機一次只服務一個 central，稱為「綁定的 central」：

| 情況 | 手機的處理 |
|---|---|
| 沒有綁定時，有 central 訂閱 `event` | 綁定它，為它建立全新的握手（鍵盤）或配對嘗試（配對畫面） |
| 綁定的 central 再次訂閱 | 視為新連線：丟棄舊的握手、session 與計數器通道，重新開始 |
| 另一個 central 訂閱，而綁定的連線已通過驗證（鍵盤）或正在配對（配對畫面） | 不理會，綁定不變 |
| 另一個 central 訂閱，而綁定的連線尚未通過驗證（鍵盤） | 改綁定到新的 central，重新開始 |
| 綁定的 central 取消訂閱，或藍牙不在開啟狀態 | 解除綁定，丟棄該連線的全部狀態 |

非綁定 central 的 `control` 寫入不交給握手或配對，唯一的例外是 §6.3 的 `notSelected` 回覆。

## 2. 分段格式

手機送出的每一則 JSON 訊息（§3.3）先編碼成位元組，再切成一個或多個分段，每個分段是一則 notification。

### 2.1 分段的版面

| 位移 | 長度 | 欄位 | 值 |
|---|---|---|---|
| 0 | 1 | 版本 | 固定 `0x02` |
| 1 | 2 | message id | UInt16 BE |
| 3 | 1 | index | 從 0 起 |
| 4 | 1 | count | 這則訊息的分段總數，1 到 255 |
| 5 | 其餘 | 訊息的一段 | |

### 2.2 切分

設 `F` 為該 central 的 notification 長度上限，`P` 為訊息的位元組長度。

1. `F` 必須大於 5，否則無法傳送。
2. `P` 不得超過 16 384，否則不傳送。
3. 每段的資料長度為 `F − 5`。分段數為 `max(1, ⌈P ÷ (F − 5)⌉)`，超過 255 則不傳送。
4. 第 `i` 段帶訊息的第 `i × (F − 5)` 個位元組起、至多 `F − 5` 個位元組。只有最後一段可以較短。長度為 0 的訊息仍送出一個只有標頭的分段。
5. 同一則訊息的分段依 index 由小到大送出。兩個分段之間可以插入指標封包（`0x03`），不可插入另一則訊息的分段。
6. message id 由手機的每個 peripheral 角色各自維護，從 0 起，每送一則訊息加 1，到 65 535 後回到 0。連線重設時不歸零。

範例：長度 600 的訊息、`F` 為 185、message id 為 `0x0102` 時，共 4 段，標頭依序為 `02 01 02 00 04`、`02 01 02 01 04`、`02 01 02 02 04`、`02 01 02 03 04`，資料長度依序為 180、180、180、60。

### 2.3 重組

主機對每條連線維護一個重組器，一次只保留一則未完成的訊息，連線結束時清空。對每個 `0x02` 分段依序檢查：

| 條件 | 處理 |
|---|---|
| 長度小於 5 | 拒收這個分段 |
| 版本不是 `0x02`，或 count 為 0 | 拒收 |
| index 不小於 count | 拒收 |
| 沒有未完成的訊息，而 index 不是 0 | 拒收 |
| message id 與未完成的訊息不同，而 index 不是 0 | 拒收，未完成的訊息保留 |
| message id 與未完成的訊息不同，而 index 是 0 | 丟棄未完成的訊息，以這個分段開始新訊息 |
| message id 相同而 count 不同 | 拒收 |
| message id 相同而該 index 已收過 | 拒收 |
| 累計資料長度超過 16 384 | 丟棄整則訊息 |

拒收只丟掉該分段，不交出任何不完整的資料。收齊 count 個分段後，依 index 順序接起來即為完整訊息。

## 3. 訊息的 JSON 形狀

### 3.1 編碼規則

傳送端必須輸出下列的正規形式。兩份實作對同一則訊息必須產生逐位元組相同的輸出。

| 項目 | 規則 |
|---|---|
| 字元編碼 | UTF-8，沒有 BOM |
| 空白 | 語彙之間沒有任何空白或換行 |
| 物件的鍵 | 依鍵名的 UTF-8 位元組值遞增排序 |
| 字串跳脫 | `"` 寫成 `\"`；`\` 寫成 `\\`；`/` 寫成 `\/`；U+0008、U+0009、U+000A、U+000C、U+000D 寫成 `\b`、`\t`、`\n`、`\f`、`\r`；其餘 U+0000 到 U+001F 寫成 `\u00xx`（小寫十六進位）；其他字元一律原樣輸出，不使用 `\u` |
| 位元組資料 | base64，標準字母表（`+` 與 `/`），含 `=` 填充，沒有換行。其中的 `/` 依字串跳脫規則寫成 `\/` |
| UUID | 36 個字元的字串，十六進位字母大寫 |
| 整數 | 十進位，沒有小數點與指數。範圍可到 64-bit 無號整數的上限，不得經由浮點數轉換 |
| 布林 | `true`、`false` |
| 沒有值的選用欄位 | 整個鍵不出現，不寫 `null` |

接收端的解碼規則：

- 接受任何鍵的順序與任何合法的 JSON 跳脫寫法。
- 物件中不認識的鍵一律忽略。
- 缺少必要欄位、欄位型別不符、base64 缺少填充或含有非字母表字元、不認識的 `type` 或列舉字串，都視為格式錯誤。
- UUID 的大小寫都接受。

### 3.2 `ControlMessage`（主機到手機，寫入 `control`）

每一則是一個只有一個鍵的物件，鍵是訊息名稱，值是該訊息的內容物件。沒有內容的訊息以空物件 `{}` 為值。只有一個未命名內容的訊息，內容放在鍵 `_0` 之下。認得的訊息名稱不是恰好一個時視為格式錯誤。`ControlMessage` 沒有 `protocolVersion` 欄位。

| 訊息 | 內容 | 何時可以明文傳送 |
|---|---|---|
| `pairAccept` | `publicKey`（65 bytes）、`hostId`（16 bytes）、`hostName`、`platform` | 配對期間 |
| `hello` | `hostId`（16 bytes）、`hostNonce`（16 bytes） | 驗證前 |
| `auth` | `proof`（32 bytes） | 驗證前 |
| `authFailed` | 無 | 任何時候 |
| `ack` | `_0`：`eventId`（UUID）、`result`（§3.5） | 不可，只能放在 `sealed` 內 |
| `status` | `_0`：`ReceiverStatus`（§9） | 不可，只能放在 `sealed` 內 |
| `bye` | 無 | 不可，只能放在 `sealed` 內 |
| `sealed` | `_0`：session 加密的輸出（§7） | 驗證後 |

`pairAccept`：

```json
{"pairAccept":{"hostId":"AAECAwQFBgcICQoLDA0ODw==","hostName":"書房的 Mac","platform":"mac","publicKey":"BGsX0fLhLEJH+Lzm5WOkQPJ3A32BLeszoPShOUXYmMKWT+NC4v4af5uO5+tKfA+eFivOM1drMV7Oy7ZAaDe\/UfU="}}
```

`hello`：

```json
{"hello":{"hostId":"AAECAwQFBgcICQoLDA0ODw==","hostNonce":"oKGio6SlpqeoqaqrrK2urw=="}}
```

`auth`：

```json

```

`authFailed`：

```json

```

`ack`（加密前的內層）：

```json
{"ack":{"_0":{"eventId":"0F8FAD5B-D9CB-469F-A165-70867728950E","result":"posted"}}}
```

`status`（加密前的內層，Mac 的例子）：

```json

```

`status`（加密前的內層，Linux 尚未取得授權的例子）：

```json

```

`bye`（加密前的內層）：

```json

```

### 3.3 `PeripheralMessage`（手機到主機，經 `event` 分段通知）

每一則是一個扁平的物件，頂層一定有 `type` 與 `protocolVersion`。v4 的 `protocolVersion` 為 4。

| `type` | 其他欄位 | 何時可以明文傳送 |
|---|---|---|
| `pairOffer` | `commitment`（32 bytes） | 配對期間 |
| `pairReveal` | `publicKey`（65 bytes）、`phoneId`（16 bytes）、`phoneName`、`phonePlatform` | 配對期間 |
| `helloReply` | `phoneNonce`（16 bytes）、`proof`（32 bytes） | 驗證前 |
| `notSelected` | 無 | 任何時候 |
| `event` | `KeyboardEvent` 的欄位，與 `type` 放在同一層（§3.4） | 不可，只能放在 `sealed` 內 |
| `sealed` | `payload`：session 加密的輸出（§7） | 驗證後 |

### 3.4 `KeyboardEvent`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `protocolVersion` | 整數 | 4 |
| `type` | 字串 | 固定 `event` |
| `eventId` | UUID | 每個事件一個新的隨機 UUID |
| `sessionId` | UUID | 鍵盤每次出現時產生一個；已驗證的連線仍在時沿用原值 |
| `seq` | 64-bit 無號整數 | 同一個 `sessionId` 內從 1 起，每個事件加 1 |
| `focusEpoch` | 64-bit 無號整數，選用 | 打這個鍵時，鍵盤最後收到的 `ReceiverStatus.focusEpoch`。還沒收到任何狀態時不帶。`ping`、`probe`、`pointerOpen`、`pointerClose` 一律不帶 |
| `kind` | 物件 | 只有一個鍵的物件，見下表 |

| `kind` | 形狀 | 意義 |
|---|---|---|
| 文字 | `{"text":{"_0":"…"}}` | 要輸入的文字，不得為空字串 |
| 退格 | `{"backspace":{}}` | 刪除游標前一個字元 |
| 換行 | `{"returnKey":{}}` | 按下 Return |
| 延遲量測 | `{"ping":{"c":整數,"s":整數}}` | `s` 是鍵盤出現的時刻，`c` 是連線完成的時刻，單位毫秒，取自手機的單調時鐘。主機只回 `pong`，不輸入任何東西 |
| 存活探測 | `{"probe":{}}` | 主機只回 `pong`。手機在 2 秒內沒有收到回覆就重設連線 |
| 開啟指標通道 | `{"pointerOpen":{"grant":整數}}` | `grant` 是鍵盤最後收到的 `ReceiverStatus.pointerGrant`（32-bit 無號整數），見 §8.5 |
| 關閉指標通道 | `{"pointerClose":{}}` | 見 §8.5 |

文字事件（加密前的內層）：

```json
{"eventId":"0F8FAD5B-D9CB-469F-A165-70867728950E","focusEpoch":7,"kind":{"text":{"_0":"A"}},"protocolVersion":4,"seq":1,"sessionId":"7C9E6679-7425-40DE-944B-E07FC1F90AE7","type":"event"}
```

退格：

```json
{"eventId":"0F8FAD5B-D9CB-469F-A165-70867728950E","focusEpoch":7,"kind":{"backspace":{}},"protocolVersion":4,"seq":2,"sessionId":"7C9E6679-7425-40DE-944B-E07FC1F90AE7","type":"event"}
```

延遲量測：

```json
{"eventId":"0F8FAD5B-D9CB-469F-A165-70867728950E","kind":{"ping":{"c":480,"s":120}},"protocolVersion":4,"seq":3,"sessionId":"7C9E6679-7425-40DE-944B-E07FC1F90AE7","type":"event"}
```

開啟指標通道：

```json
{"eventId":"0F8FAD5B-D9CB-469F-A165-70867728950E","kind":{"pointerOpen":{"grant":305419896}},"protocolVersion":4,"seq":4,"sessionId":"7C9E6679-7425-40DE-944B-E07FC1F90AE7","type":"event"}
```

### 3.5 `ack` 的結果代碼

`ack` 只表示主機已經處理該事件，不保證文字已出現在目標 App。每個事件恰好得到一個 `ack`。

| `result` | 意義 |
|---|---|
| `posted` | 已送進系統的輸入管道；對 `pointerOpen`、`pointerClose` 表示已套用 |
| `notAuthorized` | 主機沒有輸入所需的系統授權；對 `pointerOpen` 表示不允許開啟 |
| `noFocus` | 目前焦點不可輸入 |
| `staleFocus` | 事件沒有 `focusEpoch`，或它與主機目前的值不同 |
| `switchFailed` | 主機切換輸入來源失敗 |
| `compositionActive` | 主機的輸入法仍在組字，沒有輸入任何東西 |
| `injectFailed` | 主機嘗試輸入，但其中一步失敗 |
| `malformed` | 內層解密成功但無法解成事件，或文字為空字串。無法得知 `eventId` 時填 `00000000-0000-0000-0000-000000000000` |
| `pong` | `ping` 或 `probe` 的回覆 |
| `outOfOrder` | `seq` 不大於同一個 `sessionId` 已處理過的最大值，沒有輸入任何東西 |

`noFocus`、`staleFocus`、`switchFailed`、`compositionActive` 來自 Mac 的焦點安全檢查與輸入法切換。Windows 與 Linux 的接收端不做焦點檢查，也不比對 `focusEpoch`。

## 4. 身分欄位與名稱截斷規則

| 欄位 | 產生方式 | 型別 |
|---|---|---|
| `hostId` | 接收端第一次啟動時產生的 16 個亂數位元組，存在本機。重裝接收端會重新產生，等同一台新主機 | 16 bytes |
| `hostName` | 使用者可改的顯示名稱，預設為電腦名稱 | 字串，上限 32 個 UTF-8 bytes |
| `platform`（主機平台） | `mac`、`windows`、`linux` 其中之一 | 字串 |
| `phoneId` | 手機 App 第一次啟動時產生的 16 個亂數位元組，存在本機 | 16 bytes |
| `phoneName` | 預設為裝置名稱 | 字串，上限 32 個 UTF-8 bytes |
| `phonePlatform` | `ios`、`android` 其中之一 | 字串 |

名稱截斷：

1. 名稱的 UTF-8 長度不超過 32 bytes 時，原樣使用。
2. 超過時，從頭開始逐一累加完整字元（Unicode 的 extended grapheme cluster），保留累計長度不超過 32 bytes 的最長開頭，其後全部捨去。不得把一個字元切開。
3. 截斷在名稱存入本機時進行。放進訊息與金鑰推導的都是截斷後的名稱。

| 原名稱 | UTF-8 長度 | 截斷後 | 長度 |
|---|---|---|---|
| `書房的 Mac` | 13 | 不變 | 13 |
| 11 個 `測` | 33 | 10 個 `測` | 30 |
| `a` 後接 8 個 `👨‍👩‍👧`（每個 18 bytes，由 5 個碼位組成） | 145 | `a` 後接 1 個 `👨‍👩‍👧` | 19 |

儲存上限：

| 儲存者 | 每筆內容 | 上限 | 同一個識別碼再次配對 |
|---|---|---|---|
| 手機 | `hostId`、`hostName`、`platform`、`pairKey`，另記錄哪一台是目前主機 | 8 台，滿了要先刪一台才能再配對 | 覆蓋舊紀錄 |
| 主機 | `phoneId`、`phoneName`、`phonePlatform`、`pairKey` | 8 支 | 覆蓋舊紀錄 |

手機配對完成並經使用者確認後，把該主機設為目前主機。

## 5. 配對三步驟與金鑰推導

### 5.1 前提

- 手機端由配對畫面進行，鍵盤不處理配對。配對畫面出現時開始廣播配對 UUID，並開啟 120 秒的配對時段。
- 主機端由使用者開啟 120 秒的配對時段，期間掃描配對 UUID。
- 每一次配對嘗試，兩端各自產生一把全新的 P-256 金鑰，嘗試結束即丟棄，不得重複使用。
- 公鑰在線上的形式是 X9.63 未壓縮格式：`0x04 ‖ X(32, BE) ‖ Y(32, BE)`，共 65 bytes。

### 5.2 三步驟

```
手機 → pairOffer(commitment)
主機 → pairAccept(hostPublic, hostId, hostName, platform)
手機 → pairReveal(phonePublic, phoneId, phoneName, phonePlatform)
```

| 步驟 | 傳送端 | 接收端的檢查 |
|---|---|---|
| 1. `pairOffer` | central 訂閱 `event` 後手機立刻送出。`commitment` 為 `SHA-256("rk-commit"(9) ‖ phonePublic(65))` | 主機：配對時段必須開著；`commitment` 必須是 32 bytes；同一條連線只接受一次 |
| 2. `pairAccept` | 主機為這次嘗試產生金鑰後送出 | 手機：`publicKey` 必須是 65 bytes 的合法 P-256 點，且不等於自己的公鑰。通過後推導 `pairKey` 與配對碼 |
| 3. `pairReveal` | 手機在步驟 2 的檢查通過後送出 | 主機：必須已送出 `pairAccept`；以常數時間比較 `SHA-256("rk-commit" ‖ publicKey)` 與步驟 1 的 `commitment`；`publicKey` 必須是合法的 P-256 點，且不等於自己的公鑰。通過後推導 `pairKey` 與配對碼 |

主機的公鑰在手機公開自己的公鑰之前就已送出，而手機的公鑰已被 `commitment` 鎖定，所以中間人無法在看到對方公鑰後才挑選能湊出相同配對碼的金鑰。`commitment` 只涵蓋手機的公鑰。

任何一項檢查不通過、順序不符或收到其他訊息，這次嘗試即告失敗，該連線上不再接受配對訊息，已推導出的金鑰與配對碼一併丟棄。

配對畫面只處理 `pairAccept`，其他 `ControlMessage` 一律忽略。主機在配對時段以外收到 `pairOffer` 或 `pairReveal` 時不回覆，直接中斷連線。

### 5.3 金鑰推導

```
Z          = ECDH(P-256) 共享點的 X 座標(32, BE)
info       = hostPublic(65) ‖ phonePublic(65)
           ‖ hostId(16)  ‖ SHA-256(utf8(hostName)  ‖ 0x00 ‖ utf8(platform))
           ‖ phoneId(16) ‖ SHA-256(utf8(phoneName) ‖ 0x00 ‖ utf8(phonePlatform))
pairKey    = HKDF-SHA256(ikm = Z, salt = "rk-pair-v2"(10), info, 32)
```

- `info` 固定為 226 bytes。
- `hostPublic`、`phonePublic` 是線上的 65 bytes 原樣。
- `hostName`、`phoneName` 是訊息中的字串原樣，`platform`、`phonePlatform` 是訊息中的平台字串原樣。
- 兩端使用同一份 `info`：主機的項目在前，手機的項目在後，與誰在計算無關。
- 主機身分、手機身分或任一把公鑰在途中被換掉時，兩端算出的 `pairKey` 與配對碼不同。

### 5.4 配對碼

```
t      = HKDF-SHA256(ikm = pairKey, salt = 空, info = "rk-sas"(6), 4)
配對碼 = (t 視為 UInt32 BE) mod 1 000 000，寫成十進位，左邊補 0 到 6 位
```

兩端各自顯示配對碼（主機同時顯示手機名稱，手機同時顯示主機名稱），由使用者比對後各自按下確認。

- 某一端的使用者確認後，該端才把紀錄（§4）存入本機。取消、逾時、不相符或任何失敗都不儲存。
- 協定沒有「對方已確認」的訊息。主機確認後保持連線，直到手機離開、使用者結束或配對時段關閉。
- 配對時段關閉時仍未確認的嘗試一律丟棄。

## 6. 握手、逐把金鑰驗證與 `notSelected`

### 6.1 流程

```
主機 → hello(hostId, hostNonce)
手機 → helloReply(phoneNonce, phoneProof)
主機 → auth(hostProof)
```

```
phoneProof = HMAC-SHA256(key = pairKey, "phone"(5) ‖ hostNonce(16) ‖ phoneNonce(16))
hostProof  = HMAC-SHA256(key = pairKey, "host"(4)  ‖ hostNonce(16) ‖ phoneNonce(16))
```

- `hostNonce`、`phoneNonce` 各為 16 個亂數位元組，每條連線重新產生，不得重複使用。握手狀態也是每條連線一份，不跨連線保留。
- proof 的比較一律用常數時間。nonce 不是 16 bytes 或 proof 不是 32 bytes 時，不做比較直接視為不符。
- 雙方都通過後，由 `pairKey`、`hostNonce`、`phoneNonce` 推導 session 金鑰（§7）與計數器通道金鑰（§8）。
- `helloReply` 不帶 `phoneId`，握手的明文中沒有任何固定的手機識別碼。

範例（`pairKey` 取自 §5.5）：

| 項目 | 值（十六進位） |
|---|---|
| `phoneProof` | `8128de0c54393ca5a2245a1f0546ba9c721f116a6d91fdd4ce5c23a9589e4fd0` |
| `hostProof` | `0f3e240b34c3ef03cef647c3cbe1b72816af13652fea17369c8d145eebf1b359` |

### 6.2 主機端

連線就緒時：

| 情況 | 處理 |
|---|---|
| 持有至少一把配對金鑰 | 寫入 `hello`，開始 5 秒的握手計時 |
| 沒有任何配對金鑰，但配對時段開著 | 不寫入 `hello`，等待 `pairOffer`，同樣開始 5 秒計時 |
| 沒有任何配對金鑰，配對時段也沒開 | 寫入 `authFailed` 後中斷連線 |

收到 `helloReply` 時，主機不知道對方是哪一支手機，逐把金鑰驗證：

1. 必須已送出 `hello` 且尚未通過驗證，否則視為驗證失敗。
2. 依已配對手機清單的順序，對每一筆的 `pairKey` 計算 `phoneProof` 並與收到的 `proof` 比較。至多 8 次 HMAC。
3. 第一筆相符的就是這支手機，以它的 `pairKey` 完成握手：寫入 `auth(hostProof)`，連線進入已驗證狀態，隨即送出第一則加密的 `status`。
4. 全部不符，或清單是空的，視為驗證失敗。

主機同一時間只服務一支手機。兩支手機都選了同一台主機時，先連上的佔用，另一支要等前一支斷線後才連得上。

主機視為驗證失敗的情況：

| 情況 |
|---|
| 收到的位元組無法解成 `PeripheralMessage` |
| 收到明文的 `event` |
| 已驗證後收到 `pairOffer` 或 `pairReveal`；或這兩者的長度不符、公鑰不是合法的點 |
| 不在等待回覆時收到 `helloReply`，或 proof 驗不過 |
| 驗證前收到 `sealed`，或 `sealed` 解不開 |
| `sealed` 的內層是合法訊息但不是 `event` |
| 已驗證的連線上出現第二個 `sessionId`（§7.4） |

驗證失敗時，主機寫入明文的 `authFailed`、中斷連線，並且不再連線這個裝置（Mac 的範圍是到目前的接收工作階段結束為止）。配對時段開著時不列入不再連線的名單，因為它可能正是使用者要配對的手機。

握手計時到期而尚未通過驗證時，主機中斷連線，進入 §6.4 的退避。連線上已有配對嘗試時，計時不適用，改由配對時段的期限約束。

### 6.3 手機端與 `notSelected`

鍵盤只用目前主機的 `pairKey`，只和綁定的 central 握手。收到 `hello` 時：

| 情況 | 處理 |
|---|---|
| `hostId` 與目前主機的 `hostId` 逐位元組相同，來自綁定的 central，且尚未回過 `helloReply` | `hostNonce` 必須是 16 bytes。回 `helloReply` |
| `hostId` 與目前主機的不同，包括手機沒有目前主機的情況 | 只對送出這則 `hello` 的 central 通知一則明文 `notSelected`，不保存任何狀態。該 `hostId` 有沒有配對過都回同一則 |
| 上一列的 `hello` 來自綁定的 central | 回覆後解除綁定 |
| `hostId` 相符，但來自非綁定的 central | 不理會 |
| `hostId` 相符，來自綁定的 central，但這條連線已收過 `hello` | 握手失敗 |

`notSelected` 的回覆不影響已通過驗證的連線：鍵盤仍只和一個 central 握手與收發事件，對其他 central 唯一會做的事就是回 `notSelected`。

收到 `auth` 時，鍵盤驗證 `hostProof`。相符則進入已驗證狀態，可以開始送事件；不符則握手失敗。

手機視為握手失敗的情況：

| 情況 |
|---|
| `hostNonce` 不是 16 bytes |
| 同一條連線收到第二則相符的 `hello` |
| 不在等待 `auth` 時收到 `auth`，或 `hostProof` 驗不過 |
| 收到 `authFailed` |
| 已驗證後收到明文的 `ack`、`status` 或 `bye`（驗證前收到則丟棄） |
| 驗證前收到 `sealed`，或 `sealed` 解不開，或內層不是 `ack`、`status`、`bye` |

握手失敗後，這條連線不再送任何事件。手機持有配對金鑰時重設連線，讓主機可以重新連上。鍵盤收到 `pairAccept` 時不理會。

### 6.4 主機收到 `notSelected` 與握手逾時

| 項目 | 規則 |
|---|---|
| 收到 `notSelected` | 中斷連線。不顯示錯誤，不列入不再連線的名單 |
| 退避 | 10 秒（Provisional）內不連線這個裝置 |
| 退避結束後 | 要重新在廣播中看到自己的選定 UUID 才連線 |
| 握手逾時（5 秒內沒有通過驗證） | 與收到 `notSelected` 相同的退避 |

## 7. session 加密

### 7.1 金鑰

每條已驗證的連線有兩把 session 金鑰，方向各一：

```
手機到主機：K_p2m = HKDF-SHA256(ikm = pairKey, salt = 空, info = "rk-session-p2m"(14) ‖ hostNonce(16) ‖ phoneNonce(16), 32)
主機到手機：K_m2p = HKDF-SHA256(ikm = pairKey, salt = 空, info = "rk-session-m2p"(14) ‖ hostNonce(16) ‖ phoneNonce(16), 32)
```

金鑰混入兩個 nonce 與方向，所以別條連線錄下的密文、或反方向的密文都解不開。金鑰只存在記憶體，連線結束即丟棄。

### 7.2 封裝

```
輸出 = nonce(12) ‖ 密文(與明文等長) ‖ tag(16)
```

- 演算法：ChaCha20-Poly1305。
- nonce：每一則訊息重新產生的 12 個亂數位元組。
- 關聯資料：空。
- 明文：內層訊息的正規 JSON 位元組。
- 輸出以 base64 放進外層訊息：手機到主機是 `{"payload":…,"protocolVersion":4,"type":"sealed"}`，主機到手機是 `{"sealed":{"_0":…}}`。
- 輸出短於 28 bytes 或 tag 驗不過時視為解不開。

| 方向 | 金鑰 | 內層可以是 |
|---|---|---|
| 手機到主機 | `K_p2m` | 只有 `event`（§3.3 的扁平形狀，含 `type` 與 `protocolVersion`） |
| 主機到手機 | `K_m2p` | 只有 `ack`、`status`、`bye` |

驗證完成後，主機在 `control` 上除了 `sealed` 與 `authFailed` 以外不寫入任何訊息；手機在 `event` 上除了 `sealed`、`notSelected` 與指標封包以外不送任何東西。主機的 App 名稱只會出現在加密的 `status` 裡。

手機到主機的內層解密成功但無法解成訊息時（包括內層的 `protocolVersion` 不是 4），主機不視為驗證失敗，回一則 `result` 為 `malformed` 的 `ack`。

### 7.3 範例

`pairKey` 取自 §5.5，`hostNonce` 與 `phoneNonce` 取自「記號」一節。範例的 AEAD nonce 是為了能重現而指定的，實際傳送必須用亂數。

| 項目 | 值（十六進位） |
|---|---|
| `K_p2m` | `541ed5dfb6b605f8de7a1bc482e187a9599bd9215178d96cd10846bf6ecf2239` |
| `K_m2p` | `eb366bef0242e2123f4fe530b0cb5257c4cd269d21c2b8d975d37d2dfef7d968` |

| 範例 | 金鑰 | AEAD nonce | 明文 | 輸出 |
|---|---|---|---|---|
| §3.3 的 `sealed` | `K_p2m` | `000102030405060708090a0b` | §3.4 的文字事件，186 bytes | 214 bytes |
| §3.2 的 `sealed` | `K_m2p` | `101112131415161718191a1b` | §3.2 的 `ack`，83 bytes | 111 bytes |

### 7.4 事件的處理規則

| 項目 | 規則 |
|---|---|
| `sessionId` 的固定 | 主機把已驗證連線上第一個事件的 `sessionId` 記下來。同一條連線上出現別的 `sessionId` 視為驗證失敗 |
| 處理順序 | 主機依到達順序一次處理一個事件，處理完才回 `ack` 並取下一個 |
| 重複 | 主機記住最近 256 個已處理事件的 `eventId` 與結果。同一個 `eventId` 再次出現時回原本的結果，不再輸入 |
| 亂序 | 新的 `eventId` 而 `seq` 不大於同一個 `sessionId` 已處理過的最大值時，回 `outOfOrder`，不輸入。`sessionId` 改變時最大值歸零 |
| 不經過上述兩項檢查的事件 | `ping`、`probe`、`pointerOpen`、`pointerClose`，收到即回覆，不記入紀錄 |
| 不重送 | 手機不重送事件。連線中斷時還沒收到 `ack` 的事件一律放棄，因為主機可能已經輸入 |
| `seq` 的回收 | 事件編碼失敗而沒有交給無線電時，它不佔用 `seq`，下一個事件沿用同一個號碼 |
| `status` | 驗證完成後主機立刻送第一則，之後內容有變就再送 |
| `bye` | 主機要主動結束連線時（停止接收、閒置逾時、解除配對、結束程式）在中斷前送出。手機收到後重設連線。只能放在 `sealed` 內，所以旁人無法偽造 |

## 8. 計數器通道封包與指標封包

指標封包不經 JSON 與分段，每個封包是一則 notification。它用自己的金鑰與計數器 nonce，和 session 金鑰分開。

### 8.1 信封

| 位移 | 長度 | 欄位 | 說明 |
|---|---|---|---|
| 0 | 1 | magic | 指標通道為 `0x03`。明文，列入關聯資料 |
| 1 | 8 | counter | UInt64 BE，每把金鑰從 1 起。明文，列入關聯資料 |
| 9 | 16 | 密文 | ChaCha20，明文為 §8.3 的 16 bytes |
| 25 | 16 | tag | Poly1305 |

封包固定為 41 bytes。

```
K_ptr    = HKDF-SHA256(ikm = pairKey, salt = 空, info = "rk-pointer-p2m"(14) ‖ hostNonce(16) ‖ phoneNonce(16), 32)
nonce    = "PTR3"(4) ‖ counter(8, BE)
關聯資料 = 封包的位元組 0 到 8
```

方向只有手機到主機。

範例（`pairKey` 取自 §5.5，`hostNonce` 與 `phoneNonce` 取自「記號」一節，計數器為 1）：

| 項目 | 值（十六進位） |
|---|---|
| `K_ptr` | `4c23e2029084d213e4609bc0e0cc5ae79414f8ac9fa2a1ac5e65339e12b20730` |
| 明文：移動，`buttons` 為 `0x10`，`dx` 為 24，`dy` 為 −8，`dt` 為 83 | `01100018fff800530000000000000000` |
| AEAD nonce | `505452330000000000000001` |
| 關聯資料 | `030000000000000001` |
| 封包 | `030000000000000001171b369128ac5f5d96cd7e78ab7dda1c977165e0d5c567530c9f01d1489eda7b` |

### 8.2 計數器與防重播

傳送端：

1. 每條已驗證的連線只建立一組通道狀態（金鑰、計數器），用到連線結束。離開再進入觸控板頁、`pointerClose` 後再 `pointerOpen` 都沿用原計數器，不得歸零。只有新的握手才會有新的金鑰。
2. 計數器在封包交給無線電之前才配給。無線電拒收時該密文作廢，計數器不回收，內容下次用新的計數器重新加密。同一把金鑰下 nonce 不會重複。
3. 計數器到達 64-bit 無號整數的上限後，通道不得再送。

接收端依序檢查，任何一項不通過即丟棄該封包：

1. 長度必須是 41。
2. 第一個位元組必須是 `0x03`。
3. 防重播：記住已接受的最大計數器 `M` 與其下 64 個計數器是否見過。計數器為 0、等於 `M`、或在視窗內已見過，丟棄；比 `M` 小超過 64，丟棄；其餘繼續。
4. AEAD 驗證並解密。
5. 驗證通過後才更新視窗，所以偽造的大計數器無法推動視窗。

### 8.3 指標明文（16 bytes）

| 位移 | 長度 | 欄位 | 說明 |
|---|---|---|---|
| 0 | 1 | `opcode` | 見下表 |
| 1 | 1 | `buttons` | bit0 左鍵按住；bit1 右鍵（保留，接收端目前不據此動作）；bit2–3 必須為 0；bit4–7 觸控點數，只供診斷 |
| 2 | 2 | `dx` | Int16 BE，單位 1/16 個手機螢幕點，向右為正 |
| 4 | 2 | `dy` | Int16 BE，單位 1/16 點，向下為正 |
| 6 | 2 | `dt` | UInt16 BE，單位 0.1 毫秒：這個封包的位移所涵蓋的觸控時間 |
| 8 | 4 | `actionId` | UInt32 BE，保留，目前一律為 0 |
| 12 | 1 | `arg` | 依 `opcode` 而定 |
| 13 | 1 | `status` | bit0 無線電阻塞期間累積的位移；bit1 已捨棄過時的位移；bit2 位移超出欄位上限而被截斷；bit3–7 必須為 0 |
| 14 | 2 | `buttonSeq` | UInt16 BE，按鍵狀態的版本，見 §8.4 |

| `opcode` | 名稱 | `arg` | 接收端的動作 |
|---|---|---|---|
| `0x01` | 移動 | 0 | `dx`、`dy` 不全為 0 時移動游標；左鍵按住時為拖曳 |
| `0x02` | 捲動 | 階段：0 進行中、1 開始、2 結束、3 取消 | 以 `dx`、`dy` 捲動。沒有收到「開始」就收到「進行中」時視為開始。Windows 與 Linux 只取位移，不使用階段 |
| `0x10` | 點擊 | 低 2 bit 為按鍵（0 左、1 右），bit2–3 必須為 0，高 4 bit 為次數（1 到 3） | 左鍵依次數點擊；右鍵點一下。左鍵按住期間不執行 |
| `0x11` | 按鍵狀態 | 0 | 只套用 `buttons` 與 `buttonSeq` |
| `0x12` | 心跳 | 0 | 只套用 `buttons` 與 `buttonSeq`。有按鍵按住時手機每 100 毫秒送一個 |

下列情況整個封包視為不可讀而丟棄：長度不是 16、`opcode` 不在表中、任何必須為 0 的位元不為 0、捲動的 `arg` 大於 3、點擊的按鍵大於 1 或次數不在 1 到 3。

這一版沒有指標封包的確認與重送。按鍵狀態靠每個封包所帶的 `buttons` 與 `buttonSeq`、心跳，以及接收端的看門狗維持正確。

### 8.4 按鍵狀態與看門狗

- 每個封包都帶它所代表時刻的 `buttons` 與 `buttonSeq`。
- 接收端記住最後套用的 `buttonSeq`。只有封包的 `buttonSeq` 比它新時才依 `buttons` 調整左鍵；相同或較舊一律不改。第一個封包直接套用。
- 新舊比較用 16 位元序號算術：`(a − b) mod 65 536` 介於 1 與 32 767 之間時，`a` 比 `b` 新。
- 看門狗：每個可讀的封包都重新計時。左鍵按住而 350 毫秒沒有封包時放開左鍵；捲動進行中而 150 毫秒沒有封包時結束捲動。看門狗放開後 `buttonSeq` 不變，要更新的 `buttonSeq` 才會再按下。
- 通道關閉時，接收端放開所有按鍵、結束捲動，並清掉 `buttonSeq` 的紀錄。

### 8.5 開啟與關閉

1. 主機的「允許觸控板控制」開關打開時，`status` 帶 `pointerGrant`。每條已驗證的連線、每次開關由關轉開，主機都產生一個新值。
2. 鍵盤進入觸控板頁時送 `pointerOpen`，`grant` 填最後收到的 `pointerGrant`。
3. 主機收到後立即檢查：連線已驗證、開關仍開、`grant` 等於目前的 `pointerGrant`。全部成立則開啟通道並回 `posted`，否則回 `notAuthorized`。
4. 鍵盤收到 `posted` 後才開始送指標封包。1.5 秒內沒有回覆時改送一則新的 `pointerOpen`（新的 `eventId`），只重試一次。
5. 鍵盤離開觸控板頁時送 `pointerClose`。主機不需檢查授權，關閉通道並回 `posted`。

`pointerOpen` 與 `pointerClose` 在主機收到後立即處理，不排在文字輸入之後。

主機對每個指標封包都重新檢查：通道已開啟、連線已驗證、開關仍開。任一不成立即丟棄。

主機在下列情況關閉通道：

| 情況 | 附帶動作 |
|---|---|
| 套用 `pointerClose` | |
| 開關被關閉 | 送出不帶 `pointerGrant` 的 `status` |
| 連線中斷或驗證失敗 | |
| 連續 8 個指標封包未通過 §8.2 的檢查 | 產生新的 `pointerGrant` 並送出 `status`，鍵盤發現與開啟時的值不同後重新送 `pointerOpen` |

## 9. `ReceiverStatus` 在各平台的值

| 欄位 | 型別 | 線上的出現規則 | Mac | Windows、Linux |
|---|---|---|---|---|
| `ready` | 布林 | 一定出現 | 目前焦點可以輸入文字時為 `true` | 驗證完成且輸入後端可用時為 `true` |
| `focusEpoch` | 64-bit 無號整數 | 一定出現 | 每次焦點改變時更新 | 固定為 1 |
| `appName` | 字串 | 有值才出現 | 目前焦點所在的 App 名稱 | 不送 |
| `trusted` | 布林 | 只在 `false` 時出現；沒有這個鍵表示 `true` | 尚未取得「輔助使用」授權時為 `false` | Linux 尚未取得 portal 授權時為 `false`，其餘為 `true` |
| `measure` | 布林 | 只在 `true` 時出現 | 只有偵錯建置會送 | 不送 |
| `inputBlocked` | 布林 | 只在 `true` 時出現 | 焦點是密碼欄、安全鍵盤輸入開啟或螢幕鎖定時為 `true` | 不送 |
| `pointerGrant` | 32-bit 無號整數 | 有值才出現 | 觸控板開關打開時才送 | 與 Mac 相同 |

`status` 只在已驗證的連線上以 `sealed` 傳送。

## 10. 版本不符的處理

`protocolVersion` 只存在於手機到主機的訊息。主機解碼時先只讀取 `protocolVersion`，不是 4 就回報版本不符，之後才檢查其他欄位；因此其他版本的訊息不會被當成一般的格式錯誤。`ControlMessage` 沒有版本欄位，手機無法從單一則訊息判斷主機的版本。

| 情況 | 行為 |
|---|---|
| v4 手機遇到 v3 接收端 | 不會連線：v3 接收端掃描的是 GATT service UUID，v4 的手機不再廣播它。主 App 與手冊提示要更新電腦上的接收端 |
| v3 手機遇到 v4 接收端 | 不會連線：v4 接收端只掃描選定 UUID 與配對 UUID。接收端的未配對畫面提示要更新手機 App |
| 主機收到 `protocolVersion` 不是 4 的明文訊息 | 顯示「請更新 iPhone App」，不得靜默略過。連線的處理與無法解碼的訊息相同（§6.2） |
| `sealed` 的內層 `protocolVersion` 不是 4 | 回 `result` 為 `malformed` 的 `ack`（§7.2） |

v3 的配對金鑰在 v4 無法使用：金鑰推導的 salt 與 `info` 都不同。升級後第一次啟動時，兩端刪除舊的配對紀錄，使用者需要重新配對。
